# Service level objectives

Four user journeys, measured on the server-side request metric every service already exports
(`http_server_request_duration_seconds`, via the OpenTelemetry collector). Rules are generated by
[`docker/prometheus/generate-slo-rules.py`](../docker/prometheus/generate-slo-rules.py) into
`slo.yml`; edit the script, not the output.

| Journey | Route | Availability SLO | Latency SLO |
|---|---|---|---|
| sign-in | `POST auth/login` (AuthService) | 99.5% non-5xx | 95% within 500 ms |
| hire | `POST api/employees` (EmployeeService) | 99.5% | 95% within 500 ms |
| grant-currency | `POST api/rewards/grants` (RewardsService) | 99.5% | 95% within 500 ms |
| search | `GET api/search` (SearchService) | 99.5% | 95% within 500 ms |

A 99.5% target over 30 days is an error budget of about 3.6 hours. Only 5xx counts as a failure:
4xx, including 429, is the caller's (a rate limiter doing its job is not an outage).

## Alerts

Multiwindow, multi-burn-rate, from the Google SRE Workbook ("Alerting on SLOs"):

- **Fast burn (page):** 14.4x budget burn over 1h *and* over 5m. Two percent of the month's budget
  is gone in an hour.
- **Slow burn (ticket):** 6x over 6h *and* 30m. A slow leak, not an outage.

Requiring the short window as well is what makes an alert stop soon after the problem does.

## What is and is not verified

- The rules load into a real Prometheus (39 rules, none unhealthy), and the availability
  expressions evaluate against live data.
- **Not demonstrated:** an alert actually firing. There are no 5xx in the running stack to
  drive it, and `promtool` (whose unit tests would do this synthetically) does not run in the
  environment this was built in.
- **Route labels not confirmed for `grant-currency` and `search`:** they had no traffic, so no
  series to check the regex against. `sign-in` and `hire` matched.
- The targets are a first guess made before looking at real traffic; expect to revise them once
  there is data (ADR 0012).
- There is no Alertmanager, so firing alerts are visible in Prometheus only; nobody is notified.

## A bug this work found

Before this, **no server request metric reached Prometheus at all** - only `http_server_active_requests`.
The collector's health-probe filter was written per metric (`HasAttrOnDatapoint`), which drops the
whole metric if any datapoint carries the attribute, and every request histogram includes the
health probes. So request latency and error rate were invisible, and no SLO was possible. The filter
now drops only the probe datapoints (`docker/otel-collector/otel-collector-config.yaml`), and the
metric arrives with `service_name` and status code.
